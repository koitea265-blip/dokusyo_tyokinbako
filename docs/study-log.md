# どくしょ ちょきんばこ — 学習ログ `study.v1` 対応メモ

対象仕様: **学習ログ共通スキーマ仕様書 `study.v1` / 1.9**（本アプリの定義は §3.8）
本アプリの `appId`: **`reading-books`**（`/Reading-Books/`）
`studyLog.js` ロジック版: **1.1**（グローバル／IIFE 形態）

---

## 0. このアプリの位置づけ

本アプリは**読書記録アプリ**であり、正誤を採点する学習アプリではない。
そのため、コア層の一部（`firstTryCorrect` など）は形式を満たすための値になる。
**教師にとって意味のある情報は `unit.title`（読んだ本）と `ext`（ページ数・冊数・目標）に載る。**

`appId: "reading-books"` は仕様書 §3.1 の予約値に登録済み（仕様書 1.9）。
受信側（まなびクエスト）の許可リストにも登録済みで、送ればそのまま受理される（§9.4／本書 §9）。

---

## 1. 3層構成

仕様書 §6 の標準構成に合わせている。ビルドを持たない構成のため、
**共通・不変の層である `studyLog.js` のみを分離**し、残る2層はアプリ本体 `js/app.js` に
内包している（けいさんカードと同じ形。仕様書 §6 で認められている）。
`js/app.js` は、CSP で `'unsafe-inline'` を使わないために `index.html` から切り出したもので、
層の分け方そのものは変えていない。

| 層 | 場所 | 役割 |
|---|---|---|
| 保存（共通・不変） | `studyLog.js` | `StudyLog.saveStudyRecord()`。仕様書 §5.1.2 の参照実装と同一 |
| 組み立て（アプリ固有） | `js/app.js` §4 の `Study` | 1冊ぶんのレコードを組み立てる |
| 読み出し（アプリ固有） | `js/app.js` §5 の `loadStudyRecords()` | ふりかえり画面。**読み出し専用** |

---

## 2. レコードの粒度

**1冊を記録するごとに1レコード**を保存する。
セッションの始まりは「本を記録する操作を始めたとき」、終わりは「記録ボタンを押したとき」。

| 呼び出し位置 | 動作 |
|---|---|
| カメラ画面を開いたとき | `Study.begin('scan')` |
| ばんごう検索／手入力を開いたとき | `Study.begin('isbn' \| 'manual')` |
| 「この本を きろくする！」 | `Study.complete(book)` → `saveStudyRecord()` |
| 記録せずに画面を離れたとき／`pagehide` | `Study.cancel()`（**保存しない**） |

## 3. フィールドの割り当て

| フィールド | 値 | 理由 |
|---|---|---|
| `kind` | `session` | 記録の開始と終了がはっきりしている |
| `mode` | `scan` / `isbn` / `manual` | 本を記録した手段。英数小文字 |
| `unit.id` | `book-{ISBN13}` ／ `custom-{djb2ハッシュ}` | **ISBN は改訂されても不変の識別子**。仕様書 §2.5 の要件を満たす |
| `unit.title` | 本のタイトル | 教師が読む用。ID は表示名から生成していない |
| `unit.preset` | `false` | 児童が読んだ本であり、アプリ組み込みの単元ではない |
| `source` | ISBN あり → `course` ／ 手入力 → `custom` | 手入力の本は児童ごとに表記が異なるため横断集計から外す（§2.4） |
| `grading` | **`selfReport`** | 読書の記録は正誤判定ではなく児童の申告。`objective` と混ぜてはならない（§2.9） |
| `multiplayer` | `false` | 常に1人 |
| `elapsedMs` | 記録操作にかかった実時間 | |
| `activeMs` | 同上のうち操作していた時間。`elapsedMs` にクランプ済み（§2.8） | |
| `timeBasis` | `app` | |
| `status` | `completed` | 保存されるのは完了したレコードのみ（下記§4） |
| `summary` | `count/attempted/firstTryCorrect/correct` すべて `1` | §5 参照 |
| `items` | 1件（`q` は `unit.id`） | `attempted === items.length` を満たす（§2.7） |

### `ext`（アプリ固有・横断集計には使わない）

```jsonc
{
  "pages": 32,             // その本のページ数
  "priceYen": 990,         // その本の値段
  "rating": 4,             // 児童がつけた★（0〜5）
  "isbn": "9784834000825", // 手入力のときは null
  "memo": "きょうだいの話がおもしろかった",  // かんそう（未記入は null）
  "lookup": "auto",        // auto=自動取得 / manual=手入力 / none
  "monthKey": "2026-07",
  "monthlyBooks": 7,       // その月の累計冊数
  "monthlyGoal": 10,       // その月の目標
  "goalAchieved": false,
  "totalBooks": 42,        // 通算冊数
  "totalPages": 3180       // 通算ページ数
}
```

いずれも「明日の指導のどの判断を変えるか」を1文で言える項目に限っている（§4.2）。

- `pages` … 冊数だけでは分からない**読書量**が分かる。薄い本ばかりか、厚い本に挑戦しているか
- `rating` … 児童の手ごたえ。低評価が続く場合は本選びの支援が要る
- `memo` … 児童自身のことばによる本の紹介。**★の高いものを学級の「おすすめ」として共有できる**
- `monthlyBooks` / `monthlyGoal` … 目標に対する進み具合。未達が続く児童に声をかけられる
- `lookup` … 自動取得できない本（学校図書館の古い本など）の割合が分かる

児童を特定しうる情報・端末情報は含めていない（§4）。`ext` の大きさは 1KB 未満で、
上限 8KB に対して十分に小さい。

#### `ext.memo` の扱い

`memo` は自由入力である。`sanitizeMemo()` で次を必ず通してから載せる。

- 改行・タブ・連続空白を1つの半角スペースにつぶす（表・CSV にそのまま載せられるように）
- 200文字で切る（入力欄の上限と同じ）
- 空文字は載せず `null` にする

> **かんそうは「記録した時点」のものが残る。**
> レコードは `id` で重複排除される追記専用のログであり（§9.2）、あとから書き換える手段がない。
> リスト画面の「本の くわしく」で**あとから書いたかんそうは、学習ログには反映されない**
> （アプリ内の表示・書き出しには反映される）。
> 学級で共有したいかんそうは、本を記録する画面で書いておくこと。

## 4. 中断（`status: "aborted"`）について

本アプリでは**中断レコードを保存しない**。仕様書 §5.4 の3原則のうち
「**1問も解答していない中断は保存しない**」に該当するためである。

- 本が1冊も確定していない状態で画面を離れた場合、`summary.attempted` は 0 になる
- 未着手は `attempted` / `firstTryCorrect` / `items` のいずれにも数えない（§2.7）
- したがって学習データを持たないレコードになり、ログ枠（500件）を無駄に埋めることになる

`pagehide` では `Study.cancel()` を呼び、記録中のセッションを破棄する。
保存は「記録ボタンを押した瞬間」に同期的に完了するため、
Chromebook でタブが破棄されても**確定済みのレコードが失われることはない**。
保存と同時にセッションは終了し、次の記録は新しいレコードとして始まる
（仕様書 §5.5 でいう「`pageshow` が不要な設計」に当たる）。

---

## 5. `summary` の値について（重要）

読書記録には正誤の概念がないため、次のように固定している。

```jsonc
"summary": { "count": 1, "attempted": 1, "firstTryCorrect": 1, "correct": 1 }
```

**この `firstTryCorrect` を、他アプリの正答率と同じ土俵で扱ってはならない。**
`grading: "selfReport"` を立てているのはそのためである（§2.9）。

本アプリで意味を持つ主指標は次の3つ。

1. `summary.count` の合計 ＝ **読んだ冊数**
2. `ext.pages` の合計 ＝ **読んだページ数（読書量）**
3. `ext.goalAchieved` ＝ **月の目標の達成**

## 6. 読み出し側（児童へ還元する）

仕様書 §5.5 に従い、「きろく」→「どくしょの ふりかえり」で自分の記録を見せている。

- `study.records.v1` への**書き込み・削除は行わない**
- `appId === 'reading-books'` と `schema === 'study.v1'` の両方で絞り込む
- パース失敗時は空配列を返し、画面を壊さない
- `multiplayer: true` のレコードは学力指標から除外する（本アプリは常に `false`）

ふりかえり画面では、冊数・ページ数・月別グラフはアプリ自身の記録から、
「きろくに つかった時間」は学習ログの `activeMs` の合計から算出している。

## 7. 禁止事項の遵守（§1.2）

| 禁止事項 | 本アプリでの対応 |
|---|---|
| `localStorage.clear()` の使用 | 使用していない。`removeItem` で自アプリの3キーのみ削除 |
| リセットで `study.records.v1` を削除 | 削除しない。リセット対象は `reading_record_main_v1_*` の3キーのみ |
| SW の `activate` で他アプリのキャッシュを削除 | `reading-books-` で始まるキャッシュ以外は触れない |

容量管理は `studyLog.js` が担当する（500件を超えたら古いものから削除、`items` は最大200件）。

## 9. 収集側（まなびクエスト）との接続

本アプリのレコードは、**まなびクエスト**（`GIGAyama/Gamification`）が受信側として蓄積する。
まなびクエストにあった読書記録の手入力フォームは廃止され、
**読書の記録は本アプリだけで行う**構成になっている。

| 段階 | 担当 |
|---|---|
| 記録・保存 | 本アプリ（`study.records.v1` へ保存。外部送信はしない） |
| 送信 | 学習ポータル（`gigayama.github.io/Gamification/manabi-portal/`） |
| 受信・集計 | まなびクエスト（GAS。`STUDY_APPS` の許可リストに `reading-books` を登録済み） |

受信側は届いたレコードを「学習ログ」シートに残すのに加え、**「読書記録」シートへも自動転記**し、
冊数・ページ数をランキング・バッジ・ミッション・ポートフォリオPDFに反映する。
転記に使うのは `unit.title`（題名）と `ext` の `pages` / `rating` / `isbn` / `memo` である。

> **`elapsedMs` は読書時間ではない**（仕様書 §3.8.2）。本アプリが計測しているのは
> 「記録する操作にかかった時間」であり、受信側でも**学習時間の合計には加算されない**。
> 教師向けの表示では、読書は時間ではなく**冊数とページ数**で見る。
